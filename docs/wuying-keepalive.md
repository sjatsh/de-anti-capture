# 让无影窗口里的「远端云电脑」不休眠 —— 输入来源诊断 + 选型

> 目标：窗口里跑的是**远端云桌面（无影云电脑）**。要让**远端**不息屏/不锁屏/不断流，必须让**真实输入被无影客户端捕获并转发到远端**。
> 这跟「防本机休眠」是两回事。本文先教你**诊断无影到底怎么读输入**，再据此选注入法——不盲猜。

## 0. 为什么不能直接发消息

无影是流式客户端，它只转发**自己真正捕获到**的输入。
`PostMessage(WM_MOUSEMOVE)` 投递的是合成窗口消息，**不经内核 Raw Input Thread**；如果无影走 raw input / 轮询键态 / 低级钩子，它**根本看不到**这些投递消息——这就是你之前"发了没用"的原因。
所以第一步不是发输入，而是**搞清楚它从哪读输入**。

## 1. 诊断步骤（用观察模式数命中）

1. `npm start` 启动工具。
2. 顶部窗口列表找到**无影的窗口**加入目标。找不到就先点「显示隐藏」——全屏云电脑常是隐藏/无标题的投屏子窗口。
3. 勾选底部「**全量 API 日志(观察)**」。
4. 选中该目标 → 点「**注入**」→ 再点「**应用规则**」（让观察钩子生效）。
5. **切到无影窗口，真实地动鼠标、敲几下键盘**（必须是你本人真实操作，让它捕获到真输入）。
6. 切回本工具，看底部「**拦截日志**」标签里这些输入类 API 的**命中数**（规则卡也会显示 `命中 M`）；
   或点「打开文件」看 `%TEMP%\KeepAliveHook.log` 里的 `STAT ... hits=..` 行。

## 2. 看命中，对号入座

| 你真实操作时，命中持续上涨的 API | 说明无影走哪条路 | 该用的注入法 |
|---|---|---|
| `RegisterRawInputDevices`(启动时) + `GetRawInputData`/`GetRawInputBuffer`(动输入时涨) | **Raw Input** | 必须**真实输入**：瞬时切前台 + `SendInput`。消息注入无效 |
| `GetAsyncKeyState` / `GetKeyState` 持续涨 | **轮询键态** | `SendInput`（轮询读的是真实键态）。消息注入无效 |
| `GetCursorPos` 持续涨 | **轮询光标** | `SendInput` 真实移动 / `SetCursorPos`。消息注入无效 |
| `SetWindowsHookExW`(启动，装 `WH_KEYBOARD_LL`/`WH_MOUSE_LL`) | **低级钩子** | LL 钩子只认真实/`SendInput` 输入。消息注入无效 |
| 以上**都不涨**，输入却确实工作 | 大概率走**标准窗口消息**（或动态取址/别的进程） | 可试**后台消息注入** `PostMessage`（鼠标+键盘，且要发给真正收输入的子窗口） |

> 三条"真实输入"路线最终都指向同一个结论：**得把真输入送进无影**。区别只是它认不认 `PostMessage`——上表第 5 行认，前 4 行不认。

## 3. 重要提醒（避免误判）

- **IAT Hook 只能拦到"静态导入"的调用**。若某 API 是无影用 `GetProcAddress` 动态取址再调的，命中会是 0（"已挂 0 处"），并不代表它没用——而是拦不到。所以「全部 0 命中但输入明明能用」要警惕这种情况。
- **无影可能是多进程**（代理/串流/渲染分开）。读输入的进程未必就是顶层窗口那个 PID。若注入的进程命中全 0，换个相关进程试，或开「自动注入」让它跟随。
- **Qt 客户端**：无影是 Qt 框架（日志里能看到 `qwindows.dll` 等）。Qt 鼠标/键盘多走标准 `WM_*` 消息，但高分辨率滚轮/多设备会用 raw input——所以两条路都可能命中，以"动输入时谁涨得猛"为准。

## 4. 实测结论（stream_viewer, pid 34892, Qt5QWindowOwnDCIcon）

注入 logall 观察 + 聚焦窗口发真实无害输入（1px 微移 + F15），实测：

| 阶段 | 命中的 API | 含义 |
|---|---|---|
| **后台（不聚焦）** | **全 0，完全静默** | 不在前台时**根本不处理/转发任何输入** |
| **聚焦 + 真实鼠标** | `GetCursorPos` ×127 | 鼠标 = **轮询真实光标位置**（屏幕坐标） |
| **聚焦 + 真实键盘** | `GetKeyboardState` ×48 · `ToUnicodeEx` ×24 · `MapVirtualKeyW` ×12 · `GetKeyboardLayout` ×25 | 键盘 = **标准窗口消息**（WM_KEYDOWN→翻译） |
| 全程 | `GetRawInputData`=0 · `GetAsyncKeyState`/`GetKeyState`=0 · `SetWindowsHookEx*`=0 | **不用** raw input / 不轮询键态 / 无低级钩子 |

> 安装槽位显示它**静态导入**了 raw input/轮询/消息全套（`GetRawInputData:3 GetAsyncKeyState:10 ...`），
> 但运行时只走 `GetCursorPos`(鼠标) 和窗口消息(键盘)——可挂可观测，结论可信。

**三条硬结论：**
1. **后台静默** → 你原来的「后台 PostMessage」路线**不可能生效**：它不在前台时根本不读输入，发什么都白搭。
2. **鼠标走 `GetCursorPos`（真实光标）** → 喂鼠标必须**动真实光标**（SendInput/SetCursorPos），且**它得在前台**。
3. **键盘走窗口消息** → 理论上可 PostMessage(WM_KEYDOWN)，但同样**仅前台有效**；而且只要鼠标动了就足够重置远端空闲，键盘非必需。

## 5. 方案（二选一）

- **A. 瞬时切前台 + 真实光标微动 + 切回（可靠，建议先做）**
  每隔 N 秒把 stream_viewer 闪到前台 → `SendInput` 动一下真实光标 → 切回原窗口。
  几乎必然被 `GetCursorPos` 读到并转发到远端。代价：每次几十毫秒焦点闪烁。
- **B. 注入内部伪造输入（零闪烁，需再做 R&D）**
  注入 stream_viewer，hook 它的前台判定让它**以为自己在前台**，再 hook `GetCursorPos` 返回**缓慢漂移**的假坐标，
  使它在后台也持续"看到光标在动"并转发——全程零打扰、不动真光标。
  不确定点：① 它的前台门控是否只看 `GetForegroundWindow`（Qt 模块被 fg 钩子跳过，可能要换 hook 点）；
  ② 后台时它是否还跑转发循环。需再注入实验 1~2 轮验证。

> 现有 `fg` 前台伪装只解决"客户端自己别因空闲断开"，不产生远端输入；要让**远端云电脑**不休眠，必须叠加上面 A 或 B。

## 6. 方案 B（零闪烁）可行性实测 —— 结论：安全手段全部失败

按"先实验再动手"对 B 做了三轮注入实测（全部非破坏性、读完即卸载）：

| 实验 | 做法 | 结果 |
|---|---|---|
| B-i | `fg` 前台伪装（hook GetForegroundWindow 返回自身窗口） | 无效；且 `SkipModuleForFg` 会跳过 Qt 模块，对 Qt 的 stream_viewer 很可能根本没挂上 |
| B-ii | 后台注入激活消息 `WM_ACTIVATE`/`WM_NCACTIVATE`/`WM_ACTIVATEAPP`/`WM_SETFOCUS` | 后台仍 `{}` 静默，循环不复活——它无视"投递的"激活消息，按真实状态判定 |
| B-iii | 加挂 `GetFocus`/`GetGUIThreadInfo` 观察后台是否有焦点判活调用 | **后台对任何焦点 API 零调用**——采集线程/定时器是真挂起，没有可"透传伪装"的钩点 |

**结论：** stream_viewer 的前台门控是**内部、按真实激活状态判定**的，后台时采集循环整个挂起、不暴露任何可安全 hook 的判活调用。
B 的安全杠杆（伪装焦点 API / 注入激活消息）已全部失败。剩下的只有**有风险**的手段：

- **WndProc 子类化**：注入后改写 stream_viewer 主窗的窗口过程，吞掉 `WM_KILLFOCUS`/`WA_INACTIVE`，骗 Qt 永远 active。
- **内存改写**：定位并钉死它内部的 active 标志位。

二者都在**实时云会话的窗口上动刀**，可能导致花屏/卡死/会话断开（fg 钩子碰 Qt 就出过白屏）。且实验期间还观察到 stream_viewer 一度连**前台都不再轮询** `GetCursorPos`（会话状态可能已空闲/锁定），说明在线会话脆弱、不宜反复试。

**最终建议：B 不划算，回退方案 A（前台脉冲）**——可靠、低风险，且"切前台+真实光标"已被实测证明能让它读到并转发到远端。
